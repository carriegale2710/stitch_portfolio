01 / system problem

Why this service existed

Billing providers can retry the same webhook, send related events out of order, and experience short delivery failures. A naive handler may credit an account twice, downgrade the wrong workspace, or leave entitlements out of sync.

The goal was a small, inspectable API that records provider events once, applies subscription transitions safely, and gives the product a single source of truth for feature access.

architecture narrative

The API verifies the provider signature before any database work. An immutable event ledger enforces idempotency, while subscription transitions occur in the same transaction as the event record.

provider → verify → ledger → subscription → entitlement

invariant 01

Duplicate events are no-ops

A unique index on the provider event ID ensures retries cannot apply the same state transition twice.

invariant 02

Entitlements are derived

Feature access is calculated from subscription state rather than edited independently by request handlers.

invariant 03

Every transition is auditable

The original event payload and processing result remain available for debugging and support review.

contract choices

Return stable, product-level entitlements rather than exposing raw provider objects to the rest of the application. That isolates Stripe-specific complexity and makes a future provider migration or admin override possible without rewriting every feature check.

05 / trade-offs

Key technical decisions

decision 01

Event ledger over direct updates

Added storage and implementation cost, but made duplicate handling, audit trails, and reprocessing reliable.

simplicity vs correctness
decision 02

Sync transaction, async side effects

Subscription state updates synchronously; emails and analytics run later so provider delivery is not blocked.

latency vs reliability
decision 03

REST v1 over internal RPC

Chose a documented, testable external boundary at the cost of more request validation and versioning work.

clarity vs speed
06 / incident

Hardest failure mode

incident report

Out-of-order cancellation

A cancellation event arrived before an earlier renewal event, causing an expired subscription to appear active.

01

Reproduced

Built a replay fixture that intentionally delivered renewal and cancellation events in reverse chronological order.

02

Diagnosed

The handler trusted delivery order instead of comparing the provider event creation timestamp and subscription period.

03

Fixed

Stored provider timestamps and rejected stale transitions. Added integration tests for duplicated and reordered event sequences.
