01 / context

The problem

Solo founders in early customer discovery collect feedback across email, Discord, Twitter, and calls. The notes are unstructured, difficult to compare, and often lose their connection to the customer who raised the issue.

I wanted a deliberately small inbox that captured the feedback source, customer segment, and evidence behind a feature request without recreating a full support platform.

decision 01

Postgres over document storage

Feedback, customers, and problem clusters needed relational queries and workspace-level access rules.

flexibility vs integrity
decision 02

Human-approved AI grouping

AI can suggest related feedback, but users confirm the grouping so a poor prompt cannot change product evidence.

speed vs control
decision 03

Server actions for the MVP

They reduced API surface area and shared validation; I would move to a public API if integrations become a priority.

simplicity vs extensibility

04 / debugging

Hardest technical problem

incident report

Duplicate cluster jobs

Rapid edits to a feedback record could enqueue several similarity jobs, creating duplicate suggestions and unnecessary API cost.

01

Reproduced

Added a Playwright test that edited the same feedback record five times within a two-second window.

02

Diagnosed

Queue logs showed each edit generated a new job because the worker accepted a random job ID instead of a stable feedback ID.

03

Fixed

Used a deterministic job key and debounce window. Subsequent edits replace the pending job instead of multiplying it.

06 / reflection

What I'd do differently

Prototype imports earlier

Manual entry validated the core workflow, but a Gmail import would have tested the real adoption barrier sooner.

Add event tracing

Structured queue events would have made the duplicate-job issue visible before I reproduced it manually.

Test accessible shortcuts

Keyboard-first capture is valuable for power users, but it needs a clearer focus strategy and user testing.
